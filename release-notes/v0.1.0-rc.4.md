# ClusterBox BMC firmware v0.1.0-rc.4

**In one sentence:** a blade that reboots, is reset or loses power no
longer takes the whole PCIe fabric down with the BMC.

> [!WARNING]
> Updating reboots the BMC, and the BMC is the PCIe root complex: every
> blade loses omi0 for the length of the reboot (a few minutes). On a
> cluster whose etcd and DRBD run over omi0, plan for it; afterwards check
> `nodectl status --all`, etcd and DRBD.

## What's new

- **No fabric outage when a blade goes down.** The MT7620A root complex
  stopped answering if `openmiop-rc` had a read of a blade's memory in
  flight while that blade's link dropped; only a BMC reboot brought it
  back, and that reboot reset every blade's link. Now:
  - `openmiop-rc` sends nothing to a blade unless the link of its switch
    port has been up for 1.5 s (Data Link Layer Link Active, answered by
    the switch itself), and stops the moment it drops;
  - after a blade announces it is leaving (normal reboot), it is left
    alone until its link has dropped and come back;
  - `nodectl reset`, `poweroff` and `reboot --hard` first ask
    `openmiop-rc` to release the blade, then pulse the reset line or cut
    power.
- **Teleport in LuCI follows the LuCI port.** The default `clusterbox`
  app uses `luci` and publishes LuCI wherever uhttpd listens (e.g. 8080).
- **The Teleport agent ships with the firmware release**
  (`teleport-18.10.0-linux-mipsel.gz`), at a pinned version, instead of a
  separate "latest" release.

Full list: [CHANGELOG.md](https://github.com/roysbike/mixtile-clusterbox-mt7620a-openwrt/blob/v0.1.0-rc.4/CHANGELOG.md).

## Update

From v0.1.0-rc.3:

```sh
mixtile-update check && mixtile-update download && mixtile-update verify && mixtile-update install --yes
```

or LuCI **System → Firmware Update** → *Check for updates* → *Download &
verify* → *Install update*. Configuration, `/root/.ssh`, `/home` and
`/opt` (the Teleport agent) are kept.

After the reboot:

```sh
cat /etc/mixtile-release            # FIRMWARE_VERSION="v0.1.0-rc.4"
nodectl status --all                # every blade powered, LINK as before
tail /tmp/openmiop-rc.log           # "node N active" for every blade
```

## Known issues

- A blade that loses power or crashes **by itself** (not through
  `nodectl`) can still meet a read in flight and stop the root complex;
  the BMC then needs a reboot. The fix (the BMC never reads a blade) is
  in testing for the next release.
- A BMC reboot still resets the whole fabric (the MT7620A resets its
  PCIe core on boot); DRBD on the blades may need their nodes rebooted
  afterwards.

## Tested

On the lab Cluster Box (4 × Blade 3, Talos), with this `openmiop-rc` and
`nodectl` installed by hand:

- normal reboots of blades with `openmiop-rc` running: 4 of 4, no
  outage, other blades untouched;
- hard resets with the release first: 2 of 2 (by hand and with
  `nodectl reset`), root complex fine afterwards;
- not on hardware yet: this firmware image as a whole and an rc.3 →
  rc.4 update (image contents are verified in CI).
