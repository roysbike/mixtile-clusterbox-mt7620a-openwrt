# ClusterBox BMC firmware v0.4.3

**In one sentence:** heavy traffic from several blades into one blade no
longer hangs the BMC side of the PCIe fabric, and UPDATE in the web UI
works again.

Same OpenWrt base as v0.4.2 (25.12.6, Linux 6.12.112, packages of
2026-10-26). `omi-rc` and the fallback helper `openmiop-rc` come from
pcie-ep-net [`dd7a7a8`](https://github.com/roysbike/pcie-ep-net/commit/dd7a7a8151a5f9668ce112df8117e314da99c3db)
(v0.7.0 plus [pcie-ep-net#29](https://github.com/roysbike/pcie-ep-net/pull/29));
the helper and the protocol (v4) are unchanged. The BMC firmware of
**OpenMIOP Stack v0.6.x and v0.7.0**; the blades need no update.

## Why update

* **Fan-in wedge.** When three blades sent into one blade at full speed
  (13.3 Gbit/s into a Gen3 x2 port) while the BMC sent gateway traffic to
  that blade, the BMC's writes queued in the switch behind the load, the
  BMC's next config read of the switch port answered late, and the
  MT7620A root port stopped working after its completion timeout. The
  blades kept talking to each other, but the cluster was unreachable
  from the LAN, `nodectl` showed every blade without a link, and only a
  BMC reboot helped (seen 2026-10-25 and twice on 2026-10-27).
  `omi-rc` now:
  * turns off the completion timeout of the root port when it loads
    (`ct_off`, on by default; dmesg `pci 0000:00:00.0: omi-rc: completion
    timeout disabled`) and restores it when it unloads;
  * drops a blade only after its switch port reads as down for 100 ms in
    a row (`link_down_ms`, writable in
    `/sys/module/omi_rc/parameters/`). Under such load a late read
    returns 0 for up to 20 ms; it is logged as `link read as down
    (0x0000) for N ms, up again` and changes nothing.
* **UPDATE in the web UI** no longer fails with `clusterbox.fw_install:
  ubus status 5`: the image is verified and installed in the background
  and the page follows the progress. This works for updates *from*
  v0.4.3 on; to get to v0.4.3 see below.

Under fan-in load gateway traffic to the receiving blade is still slow
(pings up to ~200 ms, some loss): it waits behind the blade traffic in
the switch. Blade-to-blade traffic is not affected.

> [!WARNING]
> Updating reboots the BMC, and the BMC is the PCIe root complex: every
> blade link resets for ~150 s, and with it all pod traffic between the
> blades. Before the update:
>
> * check that no DRBD replica holds `out-of-sync` bits
>   (`drbdsetup status --verbose --statistics`, all `out-of-sync:0`,
>   [LINBIT/drbd#153](https://github.com/LINBIT/drbd/issues/153));
> * turn off CloudNativePG's primary isolation check
>   (`spec.probes.liveness.isolationCheck.enabled: false`) and turn it on
>   again afterwards;
> * back up the configuration (`sysupgrade -b`, SYSTEM → BACKUP).
>
> After the update check `nodectl status --all`, etcd, DRBD and the
> databases.

## Updating from v0.4.0, v0.4.1 or v0.4.2

Same base, so a normal update keeping the configuration. Check the
SHA-256 against `SHA256SUMS` first. UPDATE in the web UI of these
releases can fail with `ubus status 5` (the fix ships in v0.4.3 itself),
so install over SSH:

```sh
sudo mixtile-update check
sudo mixtile-update download
sudo mixtile-update install --yes --background
tail -f /tmp/mixtile-update/install.log
```

LuCI *Flash Firmware* works too.

From v0.3.0 (OpenWrt 23.05) follow [v0.4.0](v0.4.0.md#updating-from-v030-openwrt-2305).

## Changes since v0.4.2

**Fixed**

* `omi-rc`: completion timeout disabled on the root port, link loss
  debounced (pcie-ep-net#29, see above). Package versions `kmod-omi-rc`
  and `openmiop` 0.7.0-r2.
* Web UI firmware update: verify and install run detached
  (`mixtile-update verify|install --background`, `mixtile-update status`
  reports their progress, new rpcd method `fw_verify`); the LuCI page
  *Firmware Update* uses the same detached verify (firmware PR #34).

**Build**

* `verify-firmware.sh` rejects an `omi-rc` without the parameters
  `ct_off` and `link_down_ms`.

## Tested

* CI build from the release commit with the image checks of
  `verify-firmware.sh`.
* **Lab box, 2026-10-28** (four Blade 3 on mixtile-talos v0.7.0, Talos
  v1.14.4, Cozystack), BMC on v0.4.2 with the same `omi-rc` loaded by
  hand (built by the firmware CI from pcie-ep-net `fa4589a`, the code
  merged in `dd7a7a8`): three blades into one with iperf3 `-P 4`
  (13.3 Gbit/s), workstation pings through the BMC and five 8000-byte
  pings from the BMC to the receiving blade:

  | Run | `availwatch` / `nodectl-metrics` | late reads | blades dropped | wedge |
  | --- | --- | --- | --- | --- |
  | 30 s | stopped | 7 (0-20 ms) | 0 | no |
  | 30 s | running | 1 (0 ms) | 0 | no |
  | 60 s | running | 2 (0 ms) | 0 | no |

  The same load wedged the BMC side twice on 2026-10-27 with the old
  `omi-rc`. Afterwards etcd 3/3, DRBD with `out-of-sync` 0, CNPG
  healthy, no pod restarts.

## Known limitations

As in v0.4.2 ([CHANGELOG](../CHANGELOG.md)), plus the gateway latency
under fan-in load described above.
