# ClusterBox BMC firmware v0.4.1

**In one sentence:** a fix release on v0.4.0: `nodectl` no longer reads
the blades' PCIe config space, which could wedge the whole fabric when a
blade rebooted.

Same base as v0.4.0 (OpenWrt 25.12.6, Linux 6.12.112) and the same BMC
side of OpenMIOP (`omi-rc` and `openmiop-rc` from
[pcie-ep-net v0.6.0](https://github.com/roysbike/pcie-ep-net/releases/tag/v0.6.0),
whose BMC code is identical to v0.6.1). The BMC firmware of
**OpenMIOP Stack v0.6.0 and v0.6.1**, with
[pcie-ep-net v0.6.1](https://github.com/roysbike/pcie-ep-net/releases/tag/v0.6.1)
and [mixtile-talos v0.6.1](https://github.com/roysbike/mixtile-talos/releases/tag/v0.6.1).

## Why update

On v0.4.0, `nodectl status` checked the link on the switch port and then
read the blade's own config space (its Link Capabilities); `nodectl list`
ran `lspci`, which reads every blade. When a blade's link drops while
such a read is in flight (the blade reboots or crashes), the MT7620A root
complex runs into a completion timeout and stops answering: every config
read behind it returns 0, the rebooted blade cannot rejoin, and all
blades lose the BMC (gateway, DNS, NTP, LAN access) until the BMC
reboots. Blade-to-blade traffic keeps working.

This happened on the lab box on 2026-10-22: a `talosctl reboot` of one
blade while `nodectl status` was polled. `status` does not have to be run
by hand to hit it: `nodectl-metrics` runs it every minute, the LuCI
*Nodes* page every 5 s while it is open.

**Until you update, before rebooting or upgrading a blade:**
`/etc/init.d/nodectl-metrics stop` on the BMC, keep the LuCI *Nodes* page
closed and do not run `nodectl status` or `lspci`; start the metrics
again (`/etc/init.d/nodectl-metrics start`) once the blade is `active`.

> [!WARNING]
> Updating reboots the BMC, and the BMC is the PCIe root complex: every
> blade link resets for ~150 s, and with it all pod traffic between the
> blades. Before the update:
>
> * check that no DRBD replica holds `out-of-sync` bits
>   (`drbdsetup status --verbose --statistics`, all `out-of-sync:0`,
>   [LINBIT/drbd#153](https://github.com/LINBIT/drbd/issues/153));
> * turn off CloudNativePG's primary isolation check
>   (`spec.probes.liveness.isolationCheck.enabled: false`) and turn it on
>   again afterwards;
> * back up the configuration (`sysupgrade -b`, SYSTEM → BACKUP).
>
> After the update check `nodectl status --all`, etcd, DRBD and the
> databases.

## Updating from v0.4.0

Same base, so a normal update keeping the configuration: SYSTEM →
FIRMWARE in the web UI, LuCI *Flash Firmware*, or `mixtile-update
install`. Check the SHA-256 against `SHA256SUMS` first.

`/etc/config/nodectl` is kept as it is. The new options `ep_max_gen` and
`ep_max_width` default to Gen3 x2 (Blade 3) when they are missing; the
console archive options that v0.4.0's default config listed twice stay
twice in a kept config, which is harmless.

From v0.3.0 (OpenWrt 23.05) follow [v0.4.0](v0.4.0.md#updating-from-v030-openwrt-2305).

## Changes since v0.4.0

**Fixed**

* nodectl 2.0-7: `status` reads only the ASM2824 downstream port; the
  blade's link capabilities come from `ep_max_gen` / `ep_max_width`
  (default Gen3 x2), so a link that trained narrower or slower is still
  shown as degraded (`Gen3 x1/x2!`). `list` prints the vendor, device and
  class IDs the kernel cached at enumeration (no config access).
* The default `/etc/config/nodectl` no longer lists the console archive
  options twice.

**Added**

* LuCI: menu entry **ClusterBox UI** (next to Logout) that opens the main
  web UI (`/moci/`).
* `devmem` (busybox) for reading SoC registers on the console. Only reads
  are meant: a write to the wrong register can stop the PCIe root complex.

**Docs:** the README was restructured (EN and RU, same content).

## Tested

* nodectl 2.0-7 from the CI build, run read-only on the lab BMC
  (four blades on mixtile-talos v0.6.1): `status --all`, `status --json`
  and `list` give the same link data as 2.0-6 (Gen3 x2, max Gen3 x2).
* Not yet with this build: flashing it, and a blade reboot with
  `nodectl status` polled (the case that wedged v0.4.0).
* The rest of the image is v0.4.0 plus the two additions above; v0.4.0
  ran on the lab box since 2026-10-20, including a BMC reboot with all
  blades on Stack v0.6.1 (2026-10-22: blades back ~134 s after the BMC
  booted, no database failover, DRBD and ZFS clean).

## Known limitations

As in v0.4.0 ([CHANGELOG](../CHANGELOG.md)). A blade that disappears
without the leave handshake can still race a config read of `omi-rc`
itself (it reads a blade's config space only behind its own link
gating, and never its BAR: push mode).
