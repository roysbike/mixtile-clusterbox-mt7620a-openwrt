# ClusterBox BMC firmware v0.4.4

**In one sentence:** the web UI shows when a host on the OCuLink port has
taken over the PCIe uplink or the slot control of the box.

Same OpenWrt base as v0.4.3 (25.12.6, Linux 6.12.112, packages of
2026-10-26). `omi-rc` and the fallback helper `openmiop-rc` come from the
pcie-ep-net [v0.7.1](https://github.com/roysbike/pcie-ep-net/releases/tag/v0.7.1)
tag (`0566ec3`); their code is the same as in v0.4.3 (`dd7a7a8`), v0.7.1
changed only the blade side. The BMC firmware of **OpenMIOP Stack v0.6.x
and v0.7.x**; the blades need no update.

## Why update

* **OCuLink status.** The V120 control board has an OCuLink port for an
  external PCIe host. Two muxes on the board decide who owns the switch
  uplink lane 0 (with its reference clock) and the backplane I2C (blade
  power and reset): the MT7620A by default, the OCuLink host when it
  pulls `CWAKEB#` on the cable low. Switching lane 0 resets the whole
  fabric, so it should never happen unnoticed. The firmware now reads the
  mux select lines (GPIO 69 `SEL_PCIE_USB`, GPIO 68 `SEL_I2C`) and
  `HOTPLUG` (GPIO 71) and shows the owner:
  * `/sys/class/gpio/sel_pcie`, `sel_i2c`, `hotplug` (read-only;
    1 = BMC, 0 = OCuLink);
  * `ubus call clusterbox topology`: `pcie.lane0` and `pcie.i2c`
    (`bmc`, `oculink` or `unknown`);
  * CLUSTER page: `OCuLink owns PCIe lane 0` (`+ slot I2C`) on the
    switch and in the PCIe fabric health line, which turns to a warning,
    as does the overall cluster state.

  The firmware never drives these pins.
* Update from the web UI works from v0.4.3 on, so this is the first
  release that can be installed with **UPDATE** in the web UI.

> [!WARNING]
> Updating reboots the BMC, and the BMC is the PCIe root complex: every
> blade link resets for ~150 s, and with it all pod traffic between the
> blades. Before the update:
>
> * check that no DRBD replica holds `out-of-sync` bits
>   (`drbdsetup status --verbose --statistics`, all `out-of-sync:0`,
>   [LINBIT/drbd#153](https://github.com/LINBIT/drbd/issues/153));
> * turn off CloudNativePG's primary isolation check
>   (`spec.probes.liveness.isolationCheck.enabled: false`) and turn it on
>   again afterwards;
> * back up the configuration (`sysupgrade -b`, SYSTEM → BACKUP).
>
> After the update check `nodectl status --all`, etcd, DRBD and the
> databases.

## Updating from v0.4.3

SYSTEM → FIRMWARE → **UPDATE** in the web UI, or over SSH:

```sh
sudo mixtile-update check
sudo mixtile-update download
sudo mixtile-update install --yes --background
tail -f /tmp/mixtile-update/install.log
```

Check the SHA-256 against `SHA256SUMS` first when flashing by hand.
From v0.4.0 to v0.4.2 install over SSH as above (their web UI can fail
with `ubus status 5`, see [v0.4.3](v0.4.3.md)). From v0.3.0 (OpenWrt
23.05) follow [v0.4.0](v0.4.0.md#updating-from-v030-openwrt-2305).

## Changes since v0.4.3

**Added**

* OCuLink mux status: GPIO export in the V120 device tree, rpcd
  `topology` fields `pcie.lane0` / `pcie.i2c`, warnings on the CLUSTER
  page (firmware PR #36). Package versions `clusterbox` r12,
  `moci-app-clusterbox` r11.

**Changed**

* `kmod-omi-rc` and `openmiop` 0.7.1-r1 from the pcie-ep-net v0.7.1 tag
  (same BMC code as v0.4.3).

## Tested

* CI build from the release commit with the image checks of
  `verify-firmware.sh`; the device tree compiled and checked with `dtc`.
* Not yet tested with an OCuLink host: without one both fields read
  `bmc` and the page shows no warning.
