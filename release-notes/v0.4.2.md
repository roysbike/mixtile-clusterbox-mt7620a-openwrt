# ClusterBox BMC firmware v0.4.2

**In one sentence:** v0.4.1 with the newest packages of OpenWrt 25.12:
the `ca-certificates` fix from the 25.12 branch and the packages feed at
its branch head.

OpenWrt v25.12.6 is still the newest 25.12 release (Linux 6.12.112).
Since that tag the `openwrt-25.12` branches moved on; this release takes
what reaches the image. The BMC side of OpenMIOP is unchanged (`omi-rc`
and `openmiop-rc` from
[pcie-ep-net v0.6.0](https://github.com/roysbike/pcie-ep-net/releases/tag/v0.6.0),
whose BMC code is identical to v0.6.1 and v0.7.0). The BMC firmware of
**OpenMIOP Stack v0.6.x and v0.7.0**.

## Why update

* **ca-certificates:** the root "emSign ECC Root CA - G3" is no longer
  trusted. It issued intermediate CA certificates for eMudhra with 8-bit
  private keys ([openwrt/openwrt#26066](https://github.com/openwrt/openwrt/pull/26066)).
  The BMC uses the bundle for HTTPS: `mixtile-update` (GitHub), apk,
  Tailscale and Teleport.
* **packages feed** at the head of `openwrt-25.12` (2026-10-26, 42
  commits on the v25.12.6 pin). Of the feed packages in the image only
  `luasocket` changes (a Lua 5.4 variant is added; the 5.1 build in the
  image is the same). Everything else in the image was already newest.

Nothing else changes: same kernel, same configuration, same web UI.

> [!WARNING]
> Updating reboots the BMC, and the BMC is the PCIe root complex: every
> blade link resets for ~150 s, and with it all pod traffic between the
> blades. Before the update:
>
> * check that no DRBD replica holds `out-of-sync` bits
>   (`drbdsetup status --verbose --statistics`, all `out-of-sync:0`,
>   [LINBIT/drbd#153](https://github.com/LINBIT/drbd/issues/153));
> * turn off CloudNativePG's primary isolation check
>   (`spec.probes.liveness.isolationCheck.enabled: false`) and turn it on
>   again afterwards;
> * back up the configuration (`sysupgrade -b`, SYSTEM → BACKUP).
>
> After the update check `nodectl status --all`, etcd, DRBD and the
> databases.

## Updating from v0.4.0 or v0.4.1

Same base, so a normal update keeping the configuration: SYSTEM →
FIRMWARE in the web UI, LuCI *Flash Firmware*, or `mixtile-update
install`. Check the SHA-256 against `SHA256SUMS` first.

> [!NOTE]
> **UPDATE in the web UI may fail** with `Failed: clusterbox.fw_install:
> ubus status 5`; nothing is installed then and the BMC keeps running
> the old firmware. The web UI of v0.4.1 and v0.4.2 verifies the image
> twice inside one call, and rpcd gives a call 30 s (one verification
> takes ~30 s on an idle BMC). The download and the verification have
> already happened, so install over SSH:
>
> ```sh
> sudo mixtile-update install --yes --background
> tail -f /tmp/mixtile-update/install.log
> ```
>
> `--background` keeps the install running if the SSH session drops; it
> repeats every check (~30-40 s), then `sysupgrade` reboots the BMC.
> Fixed in the web UI after v0.4.2 ([CHANGELOG](../CHANGELOG.md)).

From v0.3.0 (OpenWrt 23.05) follow [v0.4.0](v0.4.0.md#updating-from-v030-openwrt-2305).

## Changes since v0.4.1

**Changed**

* `ca-certificates`: "emSign ECC Root CA - G3" blacklisted (openwrt
  commit 4a686570eb, cherry-picked from `openwrt-25.12`).
* packages feed: `772e091b09` (head of `openwrt-25.12` on 2026-10-26)
  instead of the v25.12.6 pin `093d551675`. luci stays at its v25.12.6
  pin, which is also its branch head.

**Build**

* `build.sh feeds_install` removes `luci-app-weechat` from the tree: with
  the new packages feed it forms a recursive Kconfig dependency
  (`PACKAGE_luci-app-weechat depends on PACKAGE_luci-app-weechat`), and
  `make defconfig` then dropped packages of the image. The image has no
  weechat.

## Tested

* CI build from the release commit with the image checks of
  `verify-firmware.sh` (packages, nodectl, omi-rc, release identity).
* **Lab box, 2026-10-26** (four Blade 3 on mixtile-talos v0.7.0, Talos
  v1.14.4, Cozystack): update from v0.4.1. UPDATE in the web UI failed
  twice (`ubus status 5`, see the note above); installed over SSH with
  `mixtile-update install --yes --background`. `sysupgrade` started at
  20:07:29Z, the BMC was back at 20:14Z with v0.4.2 (`0b81021`), all four
  blades `online` at Gen3 x2 at 20:15:15Z (~150 s after boot). The
  configuration was kept.
* After the update: etcd 3/3, all nodes Ready, DRBD all connected with
  `out-of-sync` 0, `zpool status -x` healthy on every node, no I/O errors
  in the database logs. The box had a hung PCIe fabric before the update
  (the API was unreachable), so the CNPG isolation check could not be
  turned off first: one primary (`seaweedfs-db`) lost the API during the
  boot, was restarted by its liveness probe and CNPG failed over to the
  replica; the old primary came back as a replica, all four clusters
  healthy at 20:20Z. Operators that had lost their leader lease crashed a
  few times and recovered by themselves.
