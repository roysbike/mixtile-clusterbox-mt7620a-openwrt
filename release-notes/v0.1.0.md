# ClusterBox BMC firmware v0.1.0

**In one sentence:** the first stable ClusterBox firmware; the BMC never
reads a blade any more, so no blade, however it goes down, can stop the
PCIe fabric.

This is the BMC part of **OpenMIOP Stack v0.3.0**, with
[pcie-ep-net v0.3.0](https://github.com/roysbike/pcie-ep-net/releases/tag/v0.3.0)
and [mixtile-talos v0.3.0](https://github.com/roysbike/mixtile-talos/releases/tag/v0.3.0).
Same image contents as
[v0.1.0-rc.6](https://github.com/roysbike/mixtile-clusterbox-mt7620a-openwrt/releases/tag/v0.1.0-rc.6)
apart from the version. A BMC already on rc.6 does not need it; the
update is offered on both the `rc` and the `stable` channel.

> [!IMPORTANT]
> **Update every blade first** to pcie-ep-net v0.3
> ([mixtile-talos v0.3.0](https://github.com/roysbike/mixtile-talos/releases/tag/v0.3.0)).
> The `omi-rc` module leaves blades without push mode alone: an older
> blade would have no `omi0` to the BMC and no peer table. If you cannot,
> `touch /etc/openmiop.use-helper` before updating keeps the old helper.

> [!WARNING]
> Updating reboots the BMC, and the BMC is the PCIe root complex: every
> blade link resets. Blades on pcie-ep-net v0.3 reconnect to each other
> in ~12 s by themselves; with mixtile-talos v0.3.0 their NVMe comes back
> too (shared PERST#). On older blade images the NVMe dies and the nodes
> need a reboot. Check `nodectl status --all`, etcd and DRBD after.

## What's new since v0.1.0-rc.4

- **Push mode: `omi-rc` kernel module.** The blades write their state
  into BMC memory; the BMC only writes into blades. A read of a blade in
  flight while its link dropped (crash, power cut) stopped the MT7620A
  root complex until a BMC reboot; that read is gone. `omi0`
  (10.20.0.1, same MAC as before) now comes from the module, and the
  blades are active within ~2 s of it loading at boot.
- **Module or helper, chosen at boot.** The `openmiop` init loads
  `omi-rc`; if it does not load, it starts the userspace helper as
  before. `touch /etc/openmiop.use-helper` forces the helper.
- **nodectl 2.0-3** releases a blade through the module before
  `nodectl reset`, `poweroff` and `reboot --hard`.

Full list: [CHANGELOG.md](https://github.com/roysbike/mixtile-clusterbox-mt7620a-openwrt/blob/v0.1.0/CHANGELOG.md).

## Update

After all blades run pcie-ep-net v0.3:

```sh
mixtile-update check && mixtile-update download && mixtile-update verify && mixtile-update install --yes
```

or LuCI **System → Firmware Update**. Configuration, `/root/.ssh`,
`/home` and `/opt` are kept. Only final releases from now on:
`uci set mixtile-update.main.channel=stable; uci commit mixtile-update`
(v0.1.0 itself sets the `stable` channel by default).

After the reboot:

```sh
cat /etc/mixtile-release            # FIRMWARE_VERSION="v0.1.0", UPDATE_CHANNEL="stable"
dmesg | grep omi0                   # "node N active" seconds after "push mode"
nodectl status --all                # every blade powered, LINK Gen3 x2
```

Back to the helper without a downgrade:
`touch /etc/openmiop.use-helper && /etc/init.d/openmiop restart`.

## Known issues

- `omi-rc` does not re-enumerate the bridge windows: a blade whose BAR
  got no address is only logged (the helper does it). Not seen with
  the lab blades.
- A blade crash or power cut without a release is harmless by design,
  but was not tested on purpose.
- A BMC reboot still resets every blade link for the length of its boot.

## Tested

On the lab Cluster Box (four Blade 3 on Talos with mixtile-talos
v0.3.0-rc.1, a loaded Cozystack cluster) with v0.1.0-rc.6, the same
image contents:

- rc.5 → rc.6 update: `omi-rc` loaded by the
  init at 45.1 s, all four blades active at 46.7 s, helper not running;
  blade DNS through the BMC back the same second; NVMe live on every
  blade, etcd 3/3, no faulty DRBD resources.
- `nodectl reset` of a blade: released, link down 32 ms later, active
  again 14.5 s after the reset, Kubernetes node Ready in ~46 s.
- iperf3 between blades over `omi0`: one stream 4.3-5.1 Gbit/s on all
  12 pairs, four senders at once 25.0 Gbit/s total.

This build's image contents are verified in CI
(`scripts/clusterbox/verify-firmware.sh`).
